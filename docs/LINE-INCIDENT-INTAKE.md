# LINE 異常回報與 Google Sheets 架構

測試分支：staging/line-incident-intake-20261101；基於staging/shopee-task-checkin-20261101。沿用Node.js、Express、PostgreSQL與原有fleet outbox，沒有建立新的雲端資源或更換正式服務。

## 資料流程

LINE HTTPS webhook → 原始內容HMAC簽章 → line_events事件去重 → 綁定群組與啟用車隊驗證 → 個人填報狀態 → 資料庫交易（案件、歷程、稽核、Sheets工作）→ 提交後LINE Reply → 獨立worker同步Google Sheets。

Bot回覆不等待Google請求完成。初次回覆只確認平台收件及排程，不宣稱雲端寫入成功。使用者可查「異常進度 I000001」，依案件寫入工作的實際狀態顯示等待同步、等待設定、同步失敗或已同步。處理歷程是另一個同步工作，可在平台管理端查看，案件已同步不代表所有後續歷程都已送達。

## 指令

- 群組輸入「異常回報」：開啟同群組、同LINE帳號獨立的10分鐘填報狀態。
- 下一則普通文字為異常內容；可帶延誤、車輛異常、貨損、事故、其他類型，不帶類型則為其他。
- 亦可直接輸入「異常回報 延誤 大園倉等候裝貨超過30分鐘」。
- 「取消回報」清除該人的填報狀態。
- 「異常進度 I000001」只查本群組對應車隊的案件。
- 無車趟的一般異常允許登記；已知任務仍使用原T任務異常或「車趟異常 自訂編號 類型 說明」。
- 私訊這組車隊指令只回傳引導，沒有繞過身分綁定建立車隊案件。

填報期間既有結構化業務指令保留優先權；例如「門店車趟」不會被誤存成異常。分類＋一般內容會當成填報，分類＋原T任務編號則沿用舊指令。使用者輸入「說明」不清除尚未完成的填報。

## 增量資料與 API

migration007增加fleet_incidents.report_scope（任務／車隊），以檢查約束維持任務型異常恰有一種任務來源、車隊型恰無任務來源。既有紀錄預設任務，沒有刪除紀錄或欄位。

新增line_incident_sessions，主鍵為群組＋LINE帳號SHA256雜湊，包含車隊與到期時間；不儲存原始LINE帳號。解除群組綁定時透過外鍵清除狀態。已完成或取消的狀態刪除，過期狀態於再次填報／輸入時處理。

沿用POST /api/line/webhook、/api/fleet-ops/incidents及明細／處理API、/api/fleet-ops/jobs。沒有新增未保護的公開案件寫入API。一般異常在平台及Sheets任務欄顯示「未指定車趟」，不製造虛假T000000。

Sheets沿用「異常案件」「異常處理歷程」；既有固定資料列編號、RAW寫入、欄位核對、工作revision、租約及重試機制保留。LINE發送優先，其次異常及處理歷程，最後其他批次同步，避免條款目錄批次工作先占滿佇列。

## 測試與部署邊界

測試使用獨立wayan-staging-db叢集，外部LINE及Google HTTP以合成憑證模擬。測試包含真實HMAC路由、LINE回覆HTTP請求、Google JWT簽署及Sheets寫入adapter，不是僅測UI；外部網路mock仍不等於真實LINE→雲端驗收。

雲端部署需要獨立測試HTTPS服務、獨立測試頻道與專用Google寫入身分。不能把127.0.0.1填作LINE webhook，也不能把既有正式Render網址當作這個未部署的新分支。建立付費資源、正式部署、合併PR不在本階段範圍。

此版本未改造原本私人司機「異常 訂單編號 說明」的operational_incidents流程；該流程尚不自動寫入車隊Sheets。未串接未提供的外部爬取來源。群組填報視群組成員為授權回報者，個別成員權限、附件／照片辨識、回覆失敗自動重試或主動送出同步完成通知不在本階段範圍。

worker預設每15秒最多處理3項工作，實際同步時間受待送量、授權及Google回應影響，不承諾固定完成秒數。缺少設定時保留案件與待送紀錄，不會自動降級為公開Sheet或無簽章Webhook。
