# Codex 開發任務：蝦皮違規管理第一階段

## 目標
在現有 Wayan Node.js + Express + PostgreSQL 專案中，新增「蝦皮違規規則主檔＋違規案件＋主管人工覆核」第一階段。不得重寫既有系統，不得影響港口派車、蝦皮派車、LINE 或自有司機績效功能。

## 開發分支
`codex/shopee-violation-phase1`

## 必讀檔案
- `server/db.js`
- `server/auth.js`
- `server/audit.js`
- `server/index.js`
- `server/routes/shopee.js`
- `server/validation.js`
- `package.json`
- `docs/SHOPEE_VIOLATION_SECURITY_SPEC.md`

## 第一階段功能範圍
1. 違規規則版本主檔：版本名稱、來源文件名稱、版本更新日期、生效日、失效日、狀態（草稿/待覆核/已核准/停用）、建立人與覆核人。
2. 違規條款主檔：規則代碼、分類、違規項目原文、適用對象、來源頁碼、核對狀態（待核對/已核對）、所屬版本。
3. 違規案件：唯一案件編號、發生日期時間、車隊或自有司機（兩者至少一個且不可同時混淆）、關聯車趟識別、規則條款、事件描述、證據說明文字、案件狀態、建立人及建立時間。
4. 人工覆核：僅 admin 可覆核；可選待確認/全責/部分責任/無責，必填判定理由；未覆核案件不得產生正式罰款、評鑑扣分或內部績效點數。
5. 案件時間軸及稽核：新增案件、修改可編輯欄位、主管覆核均寫入歷史紀錄；不可提供一般刪除 API。禁止將密碼、Token、附件內容寫入 log。
6. 前端新增簡單的違規管理頁面，使用既有單頁前端風格，至少能查詢案件、建立案件、查看規則條款及由 admin 覆核。

## 安全限制
- 所有 API 一律先 requireAuth。
- 規則管理與覆核僅限 admin；dispatcher 可讀取已核准規則並建立案件、查看其可見案件。
- 第一階段不開放合作車隊、司機外部帳號存取；不可因目前 users.role 只有 admin/dispatcher 就擅自擴充外部角色。
- 每個 API 都要做伺服器端欄位驗證；SQL 一律參數化。
- 不實作檔案上傳、公開附件 URL、罰款自動計算、累犯自動計算、扣款、評鑑扣分換算、停派或停線自動處置。
- 不得回傳 stack trace、SQL、環境變數或內部路徑。
- 案件及歷史紀錄不得永久刪除；若需要更正，新增事件/異動紀錄。
- 使用現有 `logAction`，並新增案件專屬事件歷程；注意避免記錄敏感個資。
- DB schema 僅新增 CREATE TABLE IF NOT EXISTS / ALTER TABLE IF NOT EXISTS，不可 DROP、TRUNCATE 或重建既有資料表。

## 規則資料來源限制
來源 PDF 是掃描檔，部分條款、罰款金額及累犯條件尚未逐條人工核對。不得自行補寫或推測條款、金額、扣分、累犯邏輯。初始資料不可 seed 假規則；新增條款預設「待核對」，且待核對條款不可套用於案件正式責任判定。罰款與扣分欄位第一階段不需啟用。

## 測試要求
新增自動化測試，至少涵蓋：
- 未登入請求回傳 401。
- dispatcher 不得建立/修改規則或覆核（403）。
- admin 可以建立規則版本及條款。
- 待核對規則不得作為已核准規則套用。
- dispatcher 可以建立案件，但不能覆核。
- admin 覆核時必須提供理由。
- 案件覆核前不產生罰款或點數欄位/結果。
- 案件無刪除端點，歷程會保存建立與覆核事件。
- 輸入驗證及 SQL 參數化。

## 完成標準
1. `npm run lint` 通過。
2. `npm test` 通過。
3. 新增測試涵蓋上述權限及流程。
4. 回報修改檔案、DB schema、API 路由、測試結果及未完成項目。
5. 建立 PR，維持 Draft，不合併、不部署、不連正式資料庫。
6. 若發現既有架構缺陷或需求矛盾，先在 PR 說明並提出選項，不要擅自大幅重構。
