# Wayan 運輸營運管理平台｜完整流程架構與交付規格

> 文件定位：以既有 Wayan Node.js + Express + PostgreSQL 專案為唯一主系統，定義各模組責任、資料流、角色權限、狀態生命週期及上線驗收。此文件不代表尚未完成的功能已經上線。

## 1. 平台總體架構

```text
使用者入口
  ├─ Wayan Web 管理端（管理員／調度人員）
  ├─ LINE Official Account（既有 Bot；司機回報與通知）
  └─ 合作車隊回覆入口（目前沿用既有蝦皮分派 API；外部登入隔離列為後續階段）
          │
          ▼
Express API（JWT 驗證、角色授權、輸入驗證、速率限制）
  ├─ 帳號與權限
  ├─ 港口訂單／車趟
  ├─ 司機／車輛／保養／出勤
  ├─ 蝦皮路線／合作車隊／承接分派
  ├─ 違規規則／案件／申訴／罰款人工確認
  ├─ LINE Webhook／通知／排程
  └─ 稽核紀錄／系統設定
          │
          ▼
PostgreSQL（單一資料來源；交易、外鍵、唯一限制）
          │
          └─ 備份、還原演練、監控（正式環境上線門檻）
```

原則：
- 保留既有 Wayan 登入、API、資料表、LINE Bot 與營運流程；採增量式 migration，不刪除或重建既有資料。
- Web、LINE、未來合作車隊入口一律呼叫後端 API；不得由前端直接連資料庫。
- 所有重要狀態變更須由後端驗證，並留下操作者、時間、前後狀態及原因。
- 正式環境與測試環境使用不同資料庫、不同 Secrets；測試不得連正式資料庫。
- 不自動扣薪、不自動扣款、不以未核實條款自動計罰。

## 3. 標準營運流程

### A. 港口船務／派車流程

1. 調度取得船期與運輸需求，建立港口訂單。
2. 核對船名航次、櫃號、進出口別、作業地點、指定時間及車型。
3. 系統檢查訂單資料完整性，以及司機／車輛是否可用。
4. 調度指派司機與車輛，建立車趟。
5. 司機透過既有 LINE Bot 或管理端回報出車、到站、完成及異常（依現有功能實際支援項目驗收）。
6. 調度確認完成；異常案件需補充原因、時間及處理紀錄。
7. 車趟與訂單狀態更新，寫入稽核紀錄。

建議狀態生命週期：待派車 → 已派車 → 執行中 → 已完成；取消及異常應使用獨立狀態／事件，不得以覆寫方式抹除歷史。

### B. 蝦皮店到店多車隊流程

1. 匯入或新增每日路線需求：日期、起點、迄點、車型、需求車數、備註。
2. 系統依合作車隊路線設定、車型、啟用狀態、單路線上限及每日容量計算候選名單。
3. 調度確認分派數量，批次發送需求。
4. 車隊回覆承接數量或拒絕；超過容量或不符合路線設定時拒絕寫入。
5. 調度追蹤未回覆、已確認、已拒絕及缺口車數，必要時重新分派。
6. 作業完成後回填執行結果與異常；保留需求、分派及回覆歷史。

需求狀態：待分派 → 已發送／待回覆 → 部分確認或已確認 → 執行中 → 已完成／異常／取消。
容量計算需防止同一車隊同日跨路線超派；分派批次必須交易化，避免部分寫入。

### C. 違規案件與申訴流程

1. 管理員建立規則版本，登錄來源文件、版本、生效日及失效日。
2. 逐條輸入條款原文、分類、頁碼與適用對象；第二人或具權限管理員核對來源。
3. 條款全部核對後才可核准版本；只有事件發生日有效且已核准的條款可建立案件。
4. 調度建立案件，關聯車隊／自有司機、港口車趟或蝦皮需求、事件時間、描述及證據紀錄。
5. 管理員主管覆核責任：待確認、全責、部分責任、無責，必須填寫理由。
6. 當事單位提出申訴；管理員記錄成立、部分成立或不成立及理由。
7. 只有完成責任覆核且責任為全責／部分責任，才可登記罰款明細。
8. 罰款只作人工確認紀錄；不串接薪資扣款、不自動向車隊請款。
9. 案件、申訴、罰款及每次狀態變更保留完整事件歷程，不提供直接刪除。

注意：規則 PDF 若為掃描件或字跡不清，必須人工核對原文及頁碼；未確認金額、累犯級距或扣分標準不得自行推定。

## 4. 角色與權限矩陣

| 功能 | 管理員 | 調度人員 | 司機／合作車隊 |
|---|---:|---:|---:|
| 帳號、系統設定 | 管理 | 不可 | 不可 |
| 港口訂單與派車 | 管理 | 作業 | 僅本人／受指派任務（依既有 LINE 權限） |
| 司機、車輛資料 | 管理 | 作業 | 僅查看必要任務資料 |
| 蝦皮需求與分派 | 管理 | 作業 | 合作車隊隔離查看及回覆（外部登入尚待建置） |
| 違規條款版本／核對／核准 | 管理 | 唯讀已核准條款 | 不可 |
| 建立違規案件 | 可 | 可 | 後續依外部入口授權 |
| 責任覆核、申訴裁決、罰款確認 | 管理 | 不可 | 僅提交申訴／回覆 |
| 稽核紀錄 | 管理 | 依授權唯讀 | 不可 |

重要：目前既有角色主要為 admin、dispatcher。合作車隊專屬帳號、資料列隔離、司機本人身分綁定與多因子驗證，必須完成獨立設計及安全測試後才能開放外部使用，不可只靠隱藏前端按鈕。

## 5. 核心資料關聯

- users：系統帳號及角色。
- orders：港口訂單／車趟主資料；關聯 drivers、vehicles。
- drivers、vehicles、dispatch_staff、attendance_records：人員、車輛與出勤。
- shopee_routes：蝦皮每日路線需求。
- partner_fleets、fleet_routes：合作車隊及可承接路線／車型／容量。
- shopee_assignments：路線與車隊分派、要求車數、確認車數及回覆狀態。
- shopee_violation_rule_versions、shopee_violation_rules：規則版本及條款。
- shopee_violation_cases：違規案件及來源關聯。
- shopee_violation_case_events、shopee_violation_appeals、shopee_violation_fines：案件歷程、申訴及人工罰款紀錄。
- audit_logs：跨模組操作稽核。

## 6. 共通工程規範

- API：統一回應格式、輸入驗證、分頁、排序白名單、錯誤處理及速率限制。
- 資料一致性：多表狀態變更使用 PostgreSQL transaction；競爭資源使用鎖或唯一限制。
- 安全：後端每個端點驗證 JWT、帳號有效性及角色；不得相信前端傳入的角色、金額或關聯 ID。
- 隱私：司機電話、車隊聯絡資料及事故證據採最小權限；附件如導入須使用私有儲存與授權下載。
- 稽核：重要新增、修改、核准、拒絕、覆核、申訴及人工確認均留痕。
- 可復原：正式資料庫定期備份，並定期實際演練還原；不能只確認備份工作有執行。
- 監控：API 錯誤率、LINE webhook 失敗、資料庫連線、排程失敗及通知失敗須可追蹤。

## 8. 部署與費用界線

- 開發與測試先使用獨立分支及獨立測試資料庫。
- 不將測試資料庫連到正式服務，不在未核准下執行正式 migration。
- 不自動建立付費 Render 資源、資料庫或外部服務。
- 正式部署、資料搬移、付費方案及第三方通知費用，均須先列出金額與風險並取得明確同意。
- PR #14 目前屬開發審查項目；合併、部署與正式啟用需另行驗收及授權。
