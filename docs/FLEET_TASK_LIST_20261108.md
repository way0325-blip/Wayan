# 蝦皮店到店車隊任務清單

## 呈現與操作

參考Onfleet Command Center的概要指標加路線表，以及Bringg Route Monitor依車隊／日期監看與另查路線明細的模式。本系統採亮色、表格優先、車隊總覽→車隊車趟工作頁→路線明細，適合每日大量重複派單與桌面操作；手機可橫向捲動表格，重要摘要採兩欄排列。

車隊以partner_fleets ID識別，名稱來自車隊造冊，LINE群組來自既有綁定及群組造冊。北八區001、002應是各自的車隊名冊項目，不由路線文字猜測或自動建立群組。相似名稱不合併，另保留待指派、自有車隊區塊。

車隊總覽欄位：勾選、車隊／群組、需求車數、已接取趟次、總趟次、總店數、有效報到、群組車隊下拉選單、進入車趟、BOT發布已選。包含總覽全選、整隊選取、車隊內逐趟與全選／半選，搜尋與清除選取。每次指派及發布維持1～50趟，不假裝一次無限制成功。

總趟次＝非取消車趟筆數；需求車數＝非取消車趟required_checkins合計；已接取＝有效司機接取筆數，不代表車隊確認承接；總店數＝各有效車趟的不同門店數合計，同店同趟多訂單計1店，同店跨趟各計。報到來自現有有效報到紀錄。總覽只涵蓋當日已建立車趟，不把尚未建趟需求或路線範本算成已派車。

指派先勾選車趟、選擇造冊車隊，開啟既有分派確認表並填原因，儲存才改資料，不自動發送。保留原有接取／報到後禁止直接調整、容量與資源衝突檢查。路線明細使用既有可調整順序的獨立明細介面，非把所有門店塞在總覽。

## 完整路線發布

選定同一車隊車趟→BOT發布已選→預覽完整路線、目標群組、趟數／店數→人工勾選資料揭露核對→確認發布。會揭露出車時段、取貨點、全部停靠站，與舊版僅發布可接取摘要不同，此為本次使用者明確要求。其他舊通知仍保留原接取後揭露規則。複製僅寫剪貼簿，不發送。

GET /api/store-delivery/trips/:id/line-text?details=full為已登入調度／管理員完整預覽。POST /api/store-delivery/trips/batch-notify新增details=full，items每筆附groupId與原dispatch_version。後端重新核對車趟版本、既有綁定群組、車隊啟用及Bot在場，過期預覽不能發送到新群。fullDetails保存在現有工作payload，與摘要使用不同去重鍵。正常的重送不重排，同版本完整發布不重複建立工作。

完整路線不再截斷至4200字，LINE推播按4500字安全分段；每批最多5則，後續批次有各自穩定retry key，避免LINE把後段當作前段重送而忽略。長訊息可能產生多則推播用量；部分送出後失敗仍依現有工作重試，不把排隊當作送達。

## 資料與限制

GET /api/store-delivery/dispatch-board增加store_count及claimed，沿用既有授權。無新增資料表、無migration，現有日期、派車、報到、退趟、稽核與同步資料保留。停車清冊等其他功能不變。

本次測試只使用獨立本機資料庫及模擬LINE API，不向真實安樺等群組發布。UI為HTTP／JSDOM驗收，瀏覽器控制目前逾時，未宣稱真實瀏覽器視覺驗收。Free測試服務休眠會延遲，即時性受服務可用性限制。單日查詢上限1000趟，達上限顯示警示，不宣稱數據完整。
